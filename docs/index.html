Pazaryeri vitrini için Spring Boot API'si

Ürün kataloğu, sepet, sipariş, yorum ve bildirimler için bir REST API. Ön yüz ayrı bir depoda duruyor ve bu servise HTTP üzerinden bağlanıyor.

Yerelde çalıştır Uç noktalara göz at
  1. PendingStok düşülmüş ve sepet boşaltılmıştır.
  2. ProcessingHâlâ iptal edilebilir; iptalde stok geri döner.
  3. ShippedKargo firması ve takip numarası atanır.
  4. DeliveredBu noktadan sonra iade talebi açılabilir.

Ne işe yarar

Bu proje, Türkçe bir pazaryeri vitrininin ihtiyaç duyduğu sunucu tarafını sağlıyor. Kullanıcılar kayıt olup giriş yapıyor, ürünleri kategoriye, fiyata ya da isme göre süzüyor, sepete atıyor, kayıtlı adres ve kartla sipariş veriyor, sonra siparişi kargodan teslimata kadar izliyor. Yöneticiler de aynı API üzerinden katalogu, kampanyaları ve sipariş durumlarını yönetiyor.

Aynı sözleşmeyi uygulayan bir .NET sürümü de var. İki backend'in cevapları alan alan aynı olacak şekilde yazıldı; vitrin hangisine bağlanırsa bağlansın fark görmüyor. Kurallar API sözleşmesinde tek yerde toplanıyor.

GitHub Pages yalnızca statik dosya sunduğu için API burada çalışmaz. API gezgini uygulamadan alınmış OpenAPI tanımını gösterir; istek atıp denemek için uygulamayı yerelde açmanız gerekir.

Yerelde çalıştırma

Geliştirme profili bellek içi H2 veritabanıyla açılır ve örnek veriyi kendisi yükler. Redis, RabbitMQ ya da PostgreSQL kurmanız gerekmez.

  1. JDK 17 kurulu olsun ve JAVA_HOME onu göstersin. Maven kurmanıza gerek yok, depodaki sarmalayıcı kendini indirir.

  2. Depoyu klonlayıp uygulamayı başlatın:

    git clone https://github.com/MihrimatriX/backend-spring.git
cd backend-spring
./mvnw spring-boot:run          # Windows: .\mvnw.cmd spring-boot:run

  3. Konsolda Started EcommerceBackendApplication satırı göründüğünde API http://127.0.0.1:8081 adresinde dinliyordur. Swagger arayüzü /swagger-ui.html, H2 konsolu /h2-console altında açılır.

  4. Hazır hesaplardan biriyle giriş yapın:

    E-postaŞifreRol
    admin@example.comadmin123Yönetici
    user1@example.comuser123Müşteri
    user2@example.comuser123Müşteri

Docker ile tam yığın

PostgreSQL, Redis, RabbitMQ ve Flyway göçleriyle birlikte açmak isterseniz kök dizinde docker compose up --build -d yeterli. Host portlarını .env.example dosyasını .env olarak kopyalayıp değiştirebilirsiniz; API yine 8081'de açılır.

API'yi kullanma

Her uç /api/ ile başlar ve aynı zarfla cevap verir: success ve message her zaman vardır, veri data içinde gelir. Hata durumunda errorCode makinenin, message insanın okuyacağı açıklamayı taşır; doğrulama hatalarında errors alan adına göre mesajları listeler.

curl -s -X POST http://127.0.0.1:8081/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user1@example.com","password":"user123"}'

Cevaptaki data.token değerini sonraki isteklerde Authorization: Bearer … başlığıyla gönderin. Token 24 saat geçerlidir; /api/security/logout-all-devices çağrıldığında, o çağrıyı yapan token dışındakiler hemen geçersiz olur.

TOKEN=…   # girişten dönen değer
curl -s http://127.0.0.1:8081/api/cart -H "Authorization: Bearer $TOKEN"

Birkaç kural her uçta aynı işler:

  • Tarihler UTC ve Z sonekiyle yazılır, örneğin 2026-10-02T10:54:48.689Z.
  • Tutarlar TRY cinsinden ve iki ondalıklı sayıdır.
  • Sayfalı tek liste GET /api/product'tır; diğer listeler pageNumber ve pageSize alır, düz dizi döner.
  • IP başına dakikada 300 istek sınırı vardır. Aşıldığında 429 ve Retry-After başlığı gelir.
  • Her cevapta bir X-Correlation-Id bulunur. Hata bildirirken bu değeri paylaşırsanız ilgili log satırı hemen bulunur.

Sipariş akışı

Projenin en çok kural barındıran yeri sipariş oluşturma. POST /api/order şu sırayla ilerler, adımlardan biri başarısız olursa hiçbir şey kaydedilmez:

  1. Idempotency-Key başlığı geldiyse kırpılıp küçük harfe çevrilir. Aynı kullanıcı bu anahtarla daha önce sipariş verdiyse o sipariş 200 ile döner, ikinci bir sipariş açılmaz.

  2. Teslimat adresi ve ödeme yöntemi kullanıcıya ait ve aktif olmalı.

  3. Kullanıcının sunucu tarafında dolu bir sepeti varsa istenen ürünler ve adetler sepetle birebir aynı olmalı. Bu kontrol, ödeme ekranı açıkken başka sekmede sepeti değiştiren kullanıcıyı yakalar.

  4. Stok kontrol edilip düşülür. Ürünlerde iyimser kilit var: iki kişi son ürünü aynı anda alırsa biri başarılı olur, diğeri 409 alır.

  5. Fiyat indirimli satış fiyatından hesaplanır. Ara toplam 150 TRY'nin altındaysa 34,99 TRY kargo eklenir.

  6. Sipariş Pending olarak kaydedilir, sepet boşaltılır ve kullanıcıya "Sipariş alındı" bildirimi yazılır.

Müşteri siparişi Pending ya da Processing durumundayken iptal edebilir; teslim edildikten sonra iade talebi açabilir. Yönetici durumu PUT /api/order/{id}/status ile değiştirir ve her değişiklikte kullanıcıya bildirim gider. Geliştirme profilinde siparişin sahibi /demo/advance-fulfillment ile kargo adımlarını kendisi ilerletebilir, böylece bir yönetici hesabına geçmeden siparişi teslim edildi durumuna kadar götürebilirsiniz.

Proje yapısı

Kod üç pakete ayrılmış. Ayrım klasör düzeyinde; servisler repository'leri ve ayar sınıflarını doğrudan kullanıyor, araya ayrı bir arayüz katmanı konmamış.

HTTP ve filtre zinciri

Her istek korelasyon kimliği, güvenlik başlıkları, hız sınırı ve JWT doğrulama filtrelerinden geçip controller'a ulaşır.

infrastructure

web/controller rotaları tanımlar, security JWT ve filtreleri, repository Spring Data JPA sorgularını, config CORS, önbellek ve Swagger ayarlarını, messaging RabbitMQ olaylarını, data de örnek veriyi içerir.

application

service iş kurallarını, dto istek ve cevap modellerini taşır. support altında fiyat ve kargo hesabı, kart maskeleme, idempotency anahtarı gibi birden fazla servisin paylaştığı küçük parçalar var.

domain

JPA entity'leri: ürün, kategori, sipariş, sepet, yorum, kullanıcı ve diğerleri. Ortak alanlar (id, createdAt, isActive) BaseEntity'de durur.

Hata yönetimi tek yerde yapılıyor. Servisler bir kural ihlalinde ApiException fırlatıyor; GlobalExceptionHandler bunu doğru HTTP koduna ve zarfa çeviriyor. Controller metotları bu yüzden çoğunlukla tek satır: servisi çağırıp sonucu zarfa koyuyorlar.

src/main/java/com/ecommerce/backend/
├── domain/entity/            JPA entity'leri
├── application/
│   ├── dto/                  istek ve cevap modelleri
│   ├── service/              iş kuralları
│   ├── support/              paylaşılan hesaplar (fiyat, kart, idempotency)
│   └── exception/            ApiException
└── infrastructure/
    ├── config/               CORS, JWT, önbellek, Swagger, ayar sınıfları
    ├── security/             filtreler ve JWT servisi
    ├── repository/           Spring Data JPA
    ├── web/                  controller'lar ve hata yakalayıcı
    ├── messaging/            RabbitMQ (isteğe bağlı)
    └── data/                 örnek veri yükleyiciler
src/main/resources/db/migration/   Flyway göçleri (V1–V15)

Kullanılan teknolojiler

Java 17 ve Spring Boot 3.4 (Web, Security, Data JPA, Validation, Actuator, Cache). Kimlik doğrulamada JJWT, API belgesinde springdoc-openapi, mesaj kuyruğunun dayanıklılığı için Resilience4j kullanılıyor. Üretimde PostgreSQL ve Flyway, geliştirmede H2 var. Redis ve RabbitMQ isteğe bağlı, ayarlardan kapatılabiliyor.

Test

./mvnw test birim testleri, controller testlerini ve sipariş akışının entegrasyon testlerini çalıştırır. Entegrasyon testleri stok düşümünü, aynı idempotency anahtarıyla gelen tekrar isteğini ve aynı son ürün için yarışan iki siparişi kontrol eder.

Sözleşme uyumu için ayrıca bir duman testi var. Uygulama açıkken çalıştırıldığında yaklaşık 200 çağrının durum kodunu, hata kodunu ve JSON şeklini kontrol eder:

node scripts/contract-smoke.mjs run http://127.0.0.1:8081 out-spring.json

.NET sürümü de açıksa iki çıktıyı compare komutuyla karşılaştırıp aradaki her farkı görebilirsiniz.
